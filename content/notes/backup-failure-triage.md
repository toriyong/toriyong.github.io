## 개요

백업 작업이 실패했을 때 유형별로 원인을 좁히는 순서다. 백업 실패는 알림만 끄고 넘어가기 쉬운데, 그 상태로 몇 달이 지나면 복구가 필요한 날 복구할 게 없다.

## 배경

백업 실패는 대체로 다섯 가지로 나뉜다. 증상만 보면 원인이 거의 정해진다.

| 증상 | 흔한 원인 |
| --- | --- |
| 에이전트 통신 실패 | 서비스 중지, 방화벽, 인증서 만료 |
| 시작은 되는데 중간에 멈춤 | 네트워크 끊김, 저장소 가득 참, 타임아웃 |
| 특정 파일만 실패 | 잠긴 파일, 권한, 경로 길이 |
| 매번 같은 시각에 실패 | 작업 창 겹침, 자원 경합 |
| 성공인데 크기가 줄어듦 | 대상 누락 — 가장 위험 |

마지막 항목이 제일 위험하다. 작업은 "성공"으로 끝나는데 실제로는 대상이 빠져 있다. 성공·실패만 보는 모니터링으로는 절대 못 잡는다.

## 진단

### 1. 어디서 끊겼는지

```
# 에이전트 생존과 포트
systemctl status <백업에이전트>
ss -tlnp | grep -E "<에이전트 포트>"

# 백업 서버에서 대상까지
nc -zv <대상> <포트>
```

Windows 대상이면 서비스 상태와 이벤트 로그를 본다.

```powershell
Get-Service | Where-Object {$_.DisplayName -like "*Backup*"}
Get-WinEvent -LogName Application -MaxEvents 50 |
  Where-Object {$_.LevelDisplayName -in "Error","Warning"} | Format-List TimeCreated, Message
```

### 2. 저장소 여유

```
df -hT /<백업저장소>
df -i /<백업저장소>
```

중복 제거를 쓰는 장비는 **논리 용량과 물리 용량이 따로** 논다. 장비 콘솔에서 물리 여유를 확인한다. 논리로는 여유가 보이는데 물리가 가득 차 실패하는 경우가 흔하다.

### 3. 추세 확인 — 조용한 실패 잡기

```
# 백업 파일 크기를 날짜별로 나열
ls -lt --time-style=+%F /<백업경로>/ | head -20
```

전날 대비 크게 줄었으면 대상이 빠진 것이다. DB 덤프가 0바이트에 가깝거나, 디렉터리 하나가 통째로 안 들어간 경우를 의심한다.

### 4. 데이터베이스

파일 복사만으로는 정합성이 안 맞는다. 덤프나 로그 백업이 도는지 따로 본다.

```
# 덤프 파일이 실제로 유효한지 (예: MySQL)
tail -5 /<경로>/dump.sql        # 정상이면 완료 표시가 있다
```

로그 백업이 밀리면 트랜잭션 로그가 계속 자라 디스크를 채운다. DB 서버 디스크가 갑자기 차는 원인 중 하나다.

## 자주 걸리는 것

**잠긴 파일** — 열려 있는 파일은 그냥 복사가 안 된다. Windows 는 VSS, 리눅스는 LVM 스냅샷이나 애플리케이션 인식 백업을 쓴다. VSS 작성기 상태부터 본다.

```powershell
vssadmin list writers | Select-String -Pattern "Writer name|State|Last error"
```

`State` 가 `Stable` 이 아니면 해당 서비스를 재시작한다.

**인증서·자격 증명 만료** — 조용히 실패하는 전형이다. 만료일을 모니터링 항목에 넣는다.

**작업 창 겹침** — 백업과 배치 작업, 가상화 스냅샷이 같은 시간에 몰리면 서로 느려지다 타임아웃 난다. 작업 시작 시각을 분산한다.

## 운영 시 주의

- **실패 알림을 끄는 것으로 끝내지 않는다.** 원인을 못 찾겠으면 임시로 억제하되 기한을 정하고 기록한다.
- 재시도를 무한정 걸지 않는다. 운영 시간까지 밀려 들어와 서비스에 영향을 준다.
- 실패한 날은 그 세대가 비어 있는 것이다. 보관 정책상 그 세대가 만료되면 구멍이 생긴다. 실패가 연속되면 보관 기간을 임시로 늘린다.
- 백업 계정 권한을 올려서 해결하지 않는다. 권한 때문에 실패하면 **대상 경로의 권한**을 조정한다. 백업 계정이 도메인 관리자가 되는 순간 랜섬웨어의 1순위 표적이 된다.

## 실무 권장

- 성공·실패와 함께 **백업 크기와 소요 시간**을 기록한다. 조용한 실패는 이 둘로만 잡힌다.
- 월 1회는 실제로 복구해 본다. 작게라도 좋다. 성공 로그가 복구를 보장하지 않는다.
- 실패 이력을 서버별로 쌓아둔다. 같은 서버가 반복 실패하면 구성 문제이지 일시적 오류가 아니다.
