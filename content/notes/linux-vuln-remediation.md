## 개요

취약점 점검 결과를 받아 서버에 반영하는 절차다. 진단 보고서의 항목을 그대로 적용하면 서비스가 멈추는 경우가 있어, 영향도 판단이 실제 업무의 대부분이다.

## 배경

취약점 조치는 세 종류로 나뉜다. 성격이 달라서 접근법도 다르다.

| 유형 | 예 | 위험 |
| --- | --- | --- |
| 패키지 업데이트 | openssl, kernel, bash | 재기동 필요, 호환성 |
| 설정 변경 | SSH 프로토콜·암호군, 권한 비트 | 기존 연동이 끊길 수 있음 |
| 서비스 제거·중지 | telnet, rsh, 불필요 데몬 | 쓰는 데가 있으면 장애 |

가장 많이 사고가 나는 건 두 번째다. 암호군을 강화했다가 구버전 클라이언트나 모니터링 에이전트가 못 붙는 식이다.

## 절차

### 1. 실제 해당되는지 확인한다

보고서는 버전 문자열만 보고 판단하는 경우가 많다. 배포판은 **백포트**를 하기 때문에, 버전이 낮아 보여도 이미 패치된 상태일 수 있다.

```
# RHEL 계열 — 해당 CVE 가 적용됐는지
rpm -q --changelog openssl | grep -i CVE-2026-XXXX | head

# 보안 업데이트만 확인
dnf updateinfo list security
dnf updateinfo info <advisory-id>

# Ubuntu
apt list --upgradable 2>/dev/null | grep -i security
```

### 2. 영향도를 본다

패키지를 올릴 때 무엇이 같이 올라가는지 먼저 본다.

```
dnf update --assumeno openssl        # 실제 적용 없이 목록만
dnf repoquery --whatrequires openssl-libs | head
```

커널·glibc·openssl 은 재기동이 필요한지 확인한다.

```
needs-restarting -r      # RHEL: 재부팅 필요 여부
needs-restarting -s      # 재시작이 필요한 서비스 목록
```

### 3. 되돌릴 방법을 준비한다

```
# 현재 버전 기록
rpm -qa --last | head -30 > /root/pkg_before_$(date +%F).txt

# 롤백 (dnf history)
dnf history list | head
dnf history undo <ID>
```

스냅샷이 가능한 환경이면 작업 전에 뜬다. 다만 스냅샷은 백업이 아니므로 작업 후 바로 정리한다.

### 4. 적용하고 확인한다

```
dnf update-minimal --security -y     # 보안 패치만, 최소 변경
systemctl status <서비스>
ss -tlnp | head
```

## 설정 변경 시 특히 주의

SSH 암호군 강화는 자주 요구되는 항목이다.

```
# 적용 전 — 현재 서버가 제공하는 알고리즘
sshd -T | grep -Ei "ciphers|macs|kexalgorithms"

# 변경 후 반드시
sshd -t && systemctl reload sshd
```

**세션을 하나 열어둔 채로** 작업하고, 새 세션으로 접속이 되는지 확인한 뒤에 기존 세션을 닫는다. 이 순서를 어기면 잠긴다.

연동 점검 목록을 미리 만들어 둔다. 백업 에이전트, 모니터링 에이전트, 배포 도구, 파일 전송 스크립트가 SSH 를 쓰는 경우가 많다.

## 운영 시 주의

- 보안팀이 준 목록을 그대로 전부 적용하지 않는다. 항목마다 **서비스 영향 가능성**을 적어 회신하고 합의한다.
- 패치 적용은 서비스 단위로 묶어 순차 진행한다. 이중화 구성이면 한쪽씩.
- 커널 업데이트 후 구버전 커널 엔트리를 남겨둔다. 부팅 실패 시 돌아갈 곳이 된다.
- 조치 불가 항목은 **사유와 보완 통제**를 기록한다. "적용 시 OO 서비스 중단" 과 "대신 접근 제어로 차단 중" 같은 식으로. 이게 없으면 매번 같은 지적을 받는다.

## 실무 권장

- 월 단위 패치 주기를 만든다. 긴급 건만 별도로 처리하면 일상 패치가 밀리지 않는다.
- 개발 → 스테이징 → 운영 순으로 같은 패치를 태운다. 단계마다 최소 하루 간격.
- 점검 결과와 조치 이력을 서버별로 한 표에 쌓는다. 다음 점검 때 그대로 재사용된다.
