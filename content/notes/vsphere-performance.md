## 개요

"서버가 느리다"는 신고를 받았을 때 가상화 계층에서 원인을 좁히는 순서다. 게스트 안에서만 보면 원인이 안 나오는 경우가 많다.

## 배경

VM 이 느린 원인은 게스트 안이 아니라 **호스트 자원 경합**인 경우가 흔하다. 게스트에서 `top` 을 봐도 CPU 가 놀고 있는데 응답이 느린 이유가 그것이다.

핵심 지표는 넷이다. 이것만 보면 대부분 갈린다.

| 지표 | 의미 | 경고 기준 |
| --- | --- | --- |
| CPU Ready (%RDY) | vCPU 가 물리 CPU 를 기다린 시간 | 5% 초과 |
| CPU Co-Stop (%CSTP) | 멀티 vCPU 가 서로 기다린 시간 | 3% 초과 |
| Memory Ballooning / Swap | 호스트 메모리 부족 | 0 이 아니면 확인 |
| Disk Latency (GAVG) | 게스트가 느낀 I/O 지연 | 20ms 초과 |

## 진단

GUI 는 **vSphere Client → 해당 VM → 모니터 → 성능 → 고급** 에서 CPU Ready, 메모리 벌룬, 디스크 지연을 차트로 본다. 실시간은 ESXi 호스트에서 `esxtop` 이 빠르다.

```
# ESXi SSH 접속 후
esxtop
#  c 키 → CPU 화면, %RDY %CSTP 열 확인
#  m 키 → 메모리, MCTLSZ(벌룬) SWCUR(스왑) 확인
#  d 키 → 디스크 어댑터, DAVG(장비) KAVG(커널) GAVG(합계)
#  u 키 → 디바이스별
```

지연은 세 가지를 나눠 본다. **DAVG** 가 크면 스토리지 쪽, **KAVG** 가 크면 ESXi 큐 문제(보통 큐 깊이), **GAVG** 는 둘의 합으로 게스트가 실제로 느낀 값이다.

```
# vCenter 쪽에서 스크립트로 보려면 PowerCLI
Connect-VIServer <vcenter>
Get-Stat -Entity (Get-VM <VM명>) -Stat cpu.ready.summation -Realtime -MaxSamples 20 |
  Select-Object Timestamp, @{N="Ready%";E={[math]::Round($_.Value/200,2)}}
```

`cpu.ready.summation` 은 밀리초 합계라 백분율로 바꿔야 한다. 실시간(20초 간격) 기준으로 `값 / 20000 × 100` 이고, vCPU 개수로 다시 나눈다.

## 원인별 조치

**CPU Ready 가 높다** — 호스트에 vCPU 가 과할당됐다. 그 호스트의 전체 vCPU 합이 물리 코어 수의 몇 배인지 본다. **VM 의 vCPU 를 줄이는 것이 오히려 빨라지는 경우가 많다.** vCPU 8개짜리는 8개 코어가 동시에 비어야 스케줄되기 때문이다(%CSTP 가 이때 올라간다).

**메모리 벌룬·스왑이 보인다** — 호스트 메모리가 부족하다. 예약(Reservation)을 걸거나 VM 을 분산한다. 게스트 스왑과 호스트 스왑은 다르다. 호스트 스왑(SWCUR)이 걸리면 성능이 급격히 나빠진다.

**디스크 지연이 높다** — DAVG 가 크면 스토리지 또는 경로 문제다. 멀티패스 상태와 스토리지 쪽 부하를 함께 본다. 특정 데이터스토어만 그렇다면 그 LUN 에 VM 이 몰린 것이다.

**스냅샷이 남아 있다** — 의외로 흔한 원인이다. 델타 디스크가 쌓이면 I/O 가 눈에 띄게 느려진다.

```
Get-VM | Get-Snapshot | Select VM, Name, Created, SizeGB | Sort Created
```

## 운영 시 주의

- **vCPU 를 넉넉히 주는 것이 성능에 도움이 된다는 건 오해다.** 필요한 만큼만 주고, 모자라면 올린다.
- VMware Tools 버전과 가상 하드웨어 버전이 오래되면 성능 문제가 생긴다. 다만 업그레이드는 재기동이 필요하니 작업 시간을 잡는다.
- 백업 창과 성능 저하 시간대가 겹치는지 본다. 백업이 스냅샷을 쓰는 경우가 많아 원인이 거기인 적이 있다.
- 호스트 한 대만 유독 나쁘면 펌웨어·드라이버 버전을 다른 호스트와 비교한다. 클러스터 내 불일치가 원인인 경우가 있다.

## 실무 권장

- "느리다" 신고를 받으면 **언제부터, 무엇이 느린지**를 먼저 묻는다. 로그인이 느린 것과 조회가 느린 것은 전혀 다른 문제다.
- 정상일 때의 지표를 미리 재어 둔다. 비교 대상이 없으면 지금 값이 나쁜 건지 알 수 없다.
- 조치 후 같은 지표를 다시 재서 기록한다. 이 기록이 다음 증설 근거가 된다.
