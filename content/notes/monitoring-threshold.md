## 개요

모니터링을 "설치"하는 것과 "쓸모 있게 만드는" 것은 다르다. 무엇을 보고, 어디서 알릴지 정하는 쪽이 어렵다.

## 배경

모니터링이 실패하는 방식은 둘뿐이다.

- **못 잡는다** — 장애가 났는데 알림이 없다
- **너무 잡는다** — 알림이 많아 아무도 안 본다

둘 중 실무에서 더 흔하고 더 위험한 건 두 번째다. 알림 피로가 쌓이면 진짜 알림도 묻힌다. 알림 100건 중 99건이 무시해도 되는 것이면, 그 모니터링은 없는 것과 같다.

## 무엇을 볼 것인가

네 묶음으로 나누면 빠지는 게 없다.

| 묶음 | 항목 | 성격 |
| --- | --- | --- |
| 자원 | CPU, 메모리, 디스크, 네트워크 | 추세로 본다 |
| 상태 | 프로세스 생존, 포트 응답, 인증서 만료 | 참/거짓 |
| 작업 | 백업·배치 결과, 배포 성공 여부 | 참/거짓 |
| 변경 | 계정·권한 변경, 설정 변경, 로그인 실패 급증 | 보안 |

**사용자가 겪는 것**을 하나는 넣는다. CPU 가 멀쩡해도 응답이 느릴 수 있다. 외부에서 실제 페이지를 호출해 응답 시간을 재는 항목이 자원 지표 열 개보다 낫다.

## 임계치 잡기

처음부터 맞출 수 없다. 2~4주 데이터를 보고 조정한다.

- **자원은 단일 값보다 지속 시간을 함께 건다.** "CPU 90%" 가 아니라 "CPU 90% 가 10분 지속". 순간 피크는 정상이다.
- **디스크는 비율보다 추세와 잔여 시간.** 85% 경고는 500GB 디스크와 50GB 디스크에서 의미가 완전히 다르다. "현재 증가율로 7일 내 가득 참"이 행동 가능한 정보다.
- **메모리는 사용률로 보지 않는다.** 리눅스는 남는 메모리를 캐시로 쓴다. `available` 과 스왑 사용량, OOM 발생 여부를 본다.

```
free -m
vmstat 1 5                  # si/so 가 계속 움직이면 스왑 압박
grep -i "killed process" /var/log/messages
```

## 알림 설계

**알림마다 "받으면 무엇을 할지"가 정해져 있어야 한다.** 할 일이 없으면 알림이 아니라 대시보드 항목이다.

단계를 나눈다.

| 단계 | 기준 | 전달 |
| --- | --- | --- |
| 정보 | 알아두면 좋은 것 | 대시보드만 |
| 경고 | 지금은 괜찮지만 곧 문제 | 업무 시간 채널 |
| 심각 | 서비스 영향 중 | 즉시 호출 |

야간 호출로 보낼 항목은 최소로 간다. 새벽에 깨워야 할 만큼 급한지가 기준이다.

**플래핑 억제**도 걸어둔다. 상태가 오락가락하는 대상이 알림을 수십 건 쏟아내면 그것만으로 채널이 마비된다.

## 운영 시 주의

- 모니터링 서버 자체를 모니터링한다. 죽으면 "조용해서 평화롭다"로 보인다. 외부에서 heartbeat 를 받는 구성이 가장 확실하다.
- 에이전트 설치 후 방화벽·보안그룹 규칙을 정리한다. 취약점 조치로 포트를 닫을 때 이게 먼저 끊긴다.
- 점검 계정은 **읽기 전용**으로 만든다. 모니터링 계정이 관리자 권한인 구성이 흔한데, 침해 시 전 서버 접근 경로가 된다.
- 임계치를 바꾸면 왜 바꿨는지 기록한다. 안 그러면 몇 달 뒤 아무도 못 건드린다.

## 실무 권장

- 서비스 목록에 **"이 서비스가 죽으면 누가 언제 아는가"** 열을 만들어 채워본다. 빈칸이 모니터링 공백이다.
- 알림이 울렸는데 아무 조치도 안 한 항목은 한 달에 한 번 걷어낸다. 줄이는 작업을 정기화하지 않으면 알림은 늘기만 한다.
- 장애 후 회고에서 "더 일찍 알 수 있었나"를 항상 묻는다. 이 질문이 모니터링을 개선한다.
