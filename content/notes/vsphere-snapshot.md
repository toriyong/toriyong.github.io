## 개요

vSphere 스냅샷은 되돌리기 위한 임시 장치이지 백업이 아니다. 운영에서 스냅샷 때문에 생기는 장애는 거의 전부 "오래 남겨 둬서"가 원인이다.

## 배경

스냅샷을 만들면 원본 VMDK 는 읽기 전용이 되고, 이후의 모든 쓰기가 델타 디스크에 쌓인다. 델타가 커질수록 읽기는 체인을 거슬러 올라가야 하고, 쓰기는 델타를 늘린다. 성능이 떨어지고 데이터스토어가 찬다.

데이터스토어가 꽉 차면 그 위의 VM 들이 한꺼번에 멈춘다. 스냅샷 하나가 같은 데이터스토어를 쓰는 다른 서비스까지 세우는 구조다.

## 쓰는 방법

- 작업 직전에 만들고, 작업이 끝나면 바로 지운다. 하루를 넘기지 않는 것을 원칙으로 한다.
- 이름에 **용도와 날짜와 담당자**를 적는다. `patch-2026-11-14-lys` 처럼. 이름 없는 스냅샷은 지워도 되는지 아무도 모른다.
- 메모리 스냅샷은 꼭 필요할 때만 켠다. 메모리 크기만큼 파일이 더 생기고 생성·삭제가 느려진다.
- DB 서버는 가급적 스냅샷 대신 애플리케이션 백업을 쓴다. 되돌리면 트랜잭션 일관성이 깨질 수 있다.

## 점검

```
# 남아 있는 스냅샷 전수 확인 (PowerCLI)
Get-VM | Get-Snapshot | Select VM, Name, Created, SizeGB | Sort Created

# 7일 넘은 것만
Get-VM | Get-Snapshot | Where { $_.Created -lt (Get-Date).AddDays(-7) }

# 데이터스토어 여유
Get-Datastore | Select Name, @{N='UsedGB';E={[math]::Round($_.CapacityGB-$_.FreeSpaceGB)}}, CapacityGB
```

주 1회 이 세 줄을 돌려 결과를 남겨 두면 사고가 거의 나지 않는다.

## 운영 시 주의

- **삭제(통합)가 생성보다 위험하다.** 큰 델타를 통합하면 I/O 가 몰리고 시간이 오래 걸린다. 업무 시간이 아닌 때 하고, 데이터스토어 여유가 델타 크기 이상인지 확인한 뒤 시작한다.
- 통합 중에는 VM 성능이 떨어진다. 사용자 영향이 있는 시스템은 사전 공지한다.
- "스냅샷 통합 필요" 경고가 뜬 VM 은 방치하면 체인이 계속 길어진다. 발견 즉시 처리한다.
- 백업 솔루션이 스냅샷을 쓰는 경우, 백업 실패 후 스냅샷만 남는 일이 있다. 백업 실패 알림과 스냅샷 점검을 함께 본다.

## 실무 권장

- 데이터스토어 사용률 80% 알림을 걸고, 여유가 없으면 스냅샷 생성 자체를 금지한다.
- 변경 작업 절차서에 "스냅샷 생성 → 작업 → 검증 → 스냅샷 삭제"를 한 묶음으로 넣는다. 삭제가 빠진 절차서가 가장 흔한 원인이다.
- 되돌릴 일이 생길 수 있는 작업과 아닌 작업을 구분한다. 패치처럼 되돌릴 수 있는 것만 스냅샷을 쓰고, 데이터가 바뀌는 작업은 백업으로 대비한다.
